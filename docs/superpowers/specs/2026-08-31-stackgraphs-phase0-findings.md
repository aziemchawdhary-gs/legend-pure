## Gap-iteration fixes (evidence of the process, not just the destination)

Three full harness runs were needed to reach the final numbers:

| Run | Change | ImportStub MATCH | AMBIGUOUS_DISAGREE | NOT_FOUND | MISMATCH | Gate |
|---|---|---|---|---|---|---|
| 1 (baseline) | — | 12765/14010 = 91.113% | 1218 | 27 | 0 | FAIL (ratio) |
| 2 | generalization-fallthrough fix | 13983/14010 = 99.807% | 0 | 27 | 0 | FAIL (ratio, by 14) |
| 3 (final, reproduced by this task's Step 1 run) | `::` root-package fix | 13999/14010 = 99.921% | 0 | 11 | 0 | **PASS** |

**Fix 1 — 1218 spurious `AMBIGUOUS_DISAGREE` via generalization fallthrough (1218 → 0).** Every reference to a class with a same-file superclass was spuriously also "resolving" to that superclass (transitively up the hierarchy), because `PathSearch` did not stop exploring at a completed (empty-stack) match: an unconditional `defNode -> memberScope` edge, combined with an unconditional push-chain edge added for inherited-member fallthrough, let a completed search wander into a second, spurious completion at the superclass's own definition. Root-caused via temporary instrumented scratch tests (removed before commit) tracing a concrete case (`CC_Address extends CC_GeographicEntity`). Fixed by removing the `defNode -> memberScope` edge (verified to have no other legitimate producer/consumer) and replacing the immediate generalization-edge wiring with a deferred `linkGeneralizations()` pass that adds a **scope-to-scope** edge (never itself completable) instead of connecting into a definition-reaching chain.

**Fix 2 — 27 bare `::` root-package references NOT_FOUND (27 → 0).** `ImportStub.idOrPath == "::"` (Pure's literal bare-root-reference syntax, e.g. `pathToElement('::')`) degraded under `splitPath` into two empty-string segments that matched nothing in the graph, whereas Pure's own resolver special-cases `"::"` to resolve straight to the Root package. Fixed with an explicit `ROOT_PACKAGE_SYMBOL` pop and matching dispatch in `buildImportStubReference`/`buildElementReference`.

Both fixes were verified against the full 20/21-test unit suite before and after, and against three successive parity-harness runs; `MISMATCH` stayed at 0 throughout all three runs.

## Gap taxonomy

### 1. Residual `NOT_FOUND` — 11 cases, all `expected-classifier=Package` (0.079% of ImportStub total)

**Root cause, confirmed by code reading (not guessed):** `StackGraphBuilder.buildDefinitions` registers a definition only for elements returned by `source.getNewInstances()` per file. Package instances are never "new instances" owned by a single source file — they are implicit, shared namespace containers created as a side effect of parsing any element inside them, referenced from many files — so `registerDefinition`/`FileSubgraph.setDefinition` is never called on a `Package` CoreInstance itself, and no pop chain anywhere ever completes at a Package's own definition node.

Sample lines confirm this directly: `pathToElement.pure:96` (`assertIs(Root, pathToElement('Root'))` — unqualified), `pathToElement.pure:113`, `elementPath.pure:77-79,89-91`, `elementToPath.pure:157-158` (all qualified references to actual `Package` instances such as `meta::pure::functions::meta` and `meta::pure::functions::meta::tests::model`, used as `PackageableElement` arguments).

**Judgment:** modelable-with-more-gadgets, not structural. A gadget that registers each `Package` CoreInstance as its own definition (e.g. at the first file that introduces it, or in a shared synthetic subgraph alongside `_Package.SPECIAL_TYPES`) would close this. **Estimated cost: low** — one additional gadget, same shape as the existing special-types gadget.

### 2. `EnumStub` / `PropertyStub` — zero platform-corpus instances

Confirmed by direct classifier-count walk of `GraphNodeIterable.fromModelRepository(repository)`: `import=14010 enum=0 property=0` across `core`+`platform`+`system`.

- **`PropertyStub` (explained):** the only `PropertyStub` construction site in `m3-core` backs the treepath/projection grammar (`+[a, b]`), which the DSL-mapping modules use but core/platform/system Pure source does not. Zero is the *expected* count for this corpus. Validated instead by `TestBuilderProperties` (2 tests: same-file inherited property through projection — MATCHED; and, added post-review, the deliberate cross-file limitation fixture — see #3) and `TestBuilderAssociations` (1 test).
- **`EnumStub` (partially explained, not fully confirmed):** Task 5's empirical investigation found the mechanism precisely: `EnumStub` nodes are produced only by the `enumReference: qualifiedName DOT identifier` grammar production, reachable only from a **top-level `^ClassPath instanceName(prop = Enum.VALUE)` literal instance definition**. Dot-access on an enum inside a function body or an expression-context `^Class(...)` construction (i.e., ordinary Pure code) is instead grammar-routed to a call to `extractEnumValue_Enumeration_1__String_1__T_1_` and never produces an `EnumStub` at all. Task 8's own report explicitly declines to confirm this fully explains the *platform* corpus's zero count ("plausible... not confirmed"), so this task's cheap re-check is: grep confirms platform source does contain `Enum` declarations and enum-value usages, all via property-value/function-body dot-access syntax (the `extractEnumValue` path), consistent with — but not exhaustively proving — Task 5's mechanism. **Left open per Task 8's own honest framing**; validated instead by `TestBuilderMembers#testEnumValueViaEnumStub`'s synthetic top-level-instance fixture.

**Consequence for the gates:** the ImportStub-only 99.921%/0-mismatch result says nothing about `EnumStub`/`PropertyStub` correctness at scale — those two kinds are validated only at the unit-fixture level.

### 3. Cross-file inherited-member fallthrough — named, confirmed-not-supported limitation

The generalization-fallthrough fix in Gap 1 above, while fixing the spurious-completion bug, also **removed a capability that existed only as a side effect of that same bug**: the old code's same-file guard was structurally a no-op (always true, because it compared the *referencing* file to itself), so cross-file superclass member lookups worked by accident, riding the exact `defNode -> memberScope` edge that had to be removed. The new `linkGeneralizations()` adds a direct `memberScope -> superMemberScope` edge, and `FileSubgraph.addEdge` genuinely forbids that edge across files — so **cross-file inherited-member fallthrough via `PropertyStub`/`classMemberScopes` no longer works at all.**

This was caught by post-implementation review (not initially recognized), corrected in the write-up, and pinned with a dedicated regression test: `TestBuilderProperties#testCrossFileInheritedPropertyIsKnownLimitation` — base class in `base.pure`, subclass (different file) in `sub.pure`, projection in `use.pure`. Result: `subProp` (declared directly on the projected class) resolves **MATCHED**; `baseProp` (inherited, cross-file) resolves **NOT_FOUND** — exactly the predicted, limited outcome. `PropertyStub` has zero platform-scale instances (Gap 2), so this limitation is invisible to the 99.921% headline number and must be evaluated as its own named finding.

### 4. Association candidate contributions — over-approximation mechanism, minimally exercised

`addAssociationContribution` models association-declared properties on the *other* end's class via import-prefix candidate expansion (qualified exact match, or one push-chain candidate per section-import prefix + core imports + bare name for unqualified writes) plus a member-scope reentry edge (`EdgeKind.NORMAL`, fixed from an initial incorrect `FALLBACK` during review) that lets a missed member lookup fall through to the association's cross-file candidate pops via root-judgment. This is an explicit over-approximation (multiple candidate pop chains per import prefix), matching the spec §7 ask to measure it.

**Measured counts:** platform-wide, **0** — `ImportStub` queries never reach an `ASSOCIATION_CANDIDATE`-tagged pop (those pops live in member scopes, reachable only via `PropertyStub`/property lookups, and `PropertyStub` has 0 platform instances per Gap 2). At the unit-fixture level: **1 test** (`TestBuilderAssociations#testAssociationPropertyContributedCrossFile`), confirming `Outcome.MATCHED`, correct target identity, and the `ASSOCIATION_CANDIDATE` tag on the winning end node — i.e., the mechanism works exactly once, synthetically. No stress fixture with multiple ambiguous import-prefix candidates (the actual over-approximation risk) was built; **spurious-capture rate is unmeasured**.

### 5. Milestoning — `allVersions` gadget has zero test coverage of any kind

The Class-branch milestoning gadget (`isTemporal` check on stereotype stubs, gating an `allVersions` pop tagged `NodeTag.MILESTONING`) and the harness's `isMilestoningWeakMatch`/`MATCH_MILESTONING` scoring path both exist in code, but a full search of the test tree (`grep -rn "MILESTONING\|milestoning\|allVersions" src/test`) finds **no dedicated fixture at all** — not `TestBuilderAssociations` (its single test has no temporal stereotype), not any other `TestBuilder*` class. Platform-wide, `MATCH_MILESTONING` printed 0 (the report shows no line for it, meaning the outcome bucket is empty) — expected, since the milestoning pop is only reachable via the same member-scope path that `PropertyStub`'s 0-platform-instance count already forecloses. **This is a genuine, previously-unflagged coverage gap**: the milestoning gadget's correctness is currently *asserted by code review only*, never exercised by a passing (or failing) test.

**Known exception to the "builder reads only parse-time information" discipline.** For temporal (milestoned) classes, `StackGraphBuilder`'s Class branch (`StackGraphBuilder.java:153-160`) builds its member-scope pops by iterating `element`'s `properties` and `qualifiedProperties` lists — but by the time the builder runs, `MilestoningPropertyProcessor` (a post-processing compiler pass) has already mutated those very lists: it synthesizes and adds `<prop>AllVersions`, edge-point, and milestoning-dated-parameter qualified properties, and it moves each *original* milestoned property off `properties`/`qualifiedProperties` and onto a separate `originalMilestonedProperties` list that the builder never reads (`MilestoningPropertyProcessor.java:93`). So for milestoned classes, the builder is reading state produced by a post-processing pass, not raw parse-time structure — the one confirmed exception to that discipline. Three consequences follow: (1) the hand-built `allVersions` pop (added directly by the builder via `isTemporal`) coexists, in an unvalidated way, with the processor's own synthesized `<prop>AllVersions` qualified property already present on `qualifiedProperties` — the builder never checks for or reconciles this overlap; (2) a member lookup by an *original* milestoned property's name (e.g. a temporal property as originally declared, before synthesis) would resolve `NOT_FOUND` in the stack graph, because that name lives only in `originalMilestonedProperties`, while Pure's own resolver does still resolve it; and (3) this directly affects Phase 1's file-incrementality reasoning for milestoned classes — the missing milestoning fixture already demanded above (see the required-revisions list) is exactly what will surface this behavior concretely rather than leaving it as a reasoned-through prediction.

## Answers to spec §7 open questions

- **Import-group id uniqueness** (`AntlrContextToM3CoreInstance.java:3982` TODO): not directly instrumented as its own metric by any task. Indirect evidence: if duplicate import-group ids caused section-scope misbinding, the most likely visible symptom would be a `MISMATCH` (wrong section's imports consulted) or a spurious `AMBIGUOUS_DISAGREE`; both were 0 in the final run across all 14010 queries, and the one `AMBIGUOUS_DISAGREE` episode that did occur (Gap-iteration fix 1) was root-caused to a different, unrelated bug. **No adverse symptom observed**, but this was never checked directly (e.g., by counting distinct `importGroup` CoreInstances vs. distinct ids) — treat as "no negative evidence found," not "confirmed unique."
- **Generalization search-order sensitivity**: not directly tested. No diamond-inheritance or multi-supertype-order fixture exists in the unit suite (`TestBuilderProperties` covers single-level and cross-file-limitation only). The platform run's 0 `AMBIGUOUS_DISAGREE`/0 `MISMATCH` is consistent with no order-dependent case existing in this corpus, but the spike never built the adversarial fixture (multiple supertypes declaring the same member name) that would actually stress this. **Open — needs a dedicated fixture before Phase 1 can claim this is a non-issue.**
- **Projection-copied stubs** (`AntlrContextToM3CoreInstance.java:2795,2873`): this is exactly the mechanism Task 6 found and documented — `PropertyStub.owner` is always post-processing-resolved to the already-resolved owning `Class` (never an `ImportStub`), a single construction site, confirmed structural (not a fixture quirk). **Quantified: 0 in the platform corpus** (folded into Gap 2); the builder's `classMemberScopes`-based handling is validated only by the 2+1 synthetic unit fixtures described above.
- **Search-space / fan-out cost**: the Step 4 first-symbol-index contingency was **not needed**. Full harness elapsed time was 860.5 s (~14.3 min) in this task's own run (830–860 s across all three full-suite runs recorded), comfortably under the 1800 s (30 min) contingency threshold. Per-query cost is nonetheless non-trivial (~66–82 ms median-to-max, root-judgment fanning out to every file's root on each unqualified/fallback lookup) — acceptable for a query-time spike over ~hundreds of files, but the report's own concern #4 (Task 8) flags this as worth indexing before this harness is run routinely or scaled beyond the spike.
- **Association candidate over-approximation**: **0 `ASSOCIATION_CANDIDATE` matches at platform scale, 1 at unit-fixture scale** (see Gap 4). No spurious captures were observed, but none were stress-tested for either — the single fixture has exactly one candidate path, so it cannot exercise the over-approximation's actual risk (multiple distinct import-prefix candidates colliding).

## Explicit deviations from the spec, by design

1. **Negative parity uses synthetic references over valid compiled sources**, not parse-only pipelines — the spec is silent on mechanism; `TestNegativeParity` compiles fixtures that legitimately fail Pure compilation (asserting on the *cause*, not just any exception) and separately queries the stack graph via `TestAccess.addSyntheticReference`-style synthetic reference nodes with the same shape, comparing *outcomes* only (message-text parity is explicitly deferred to a later phase, per spec §4.5).
2. **Milestoning models only `allVersions`** as a weak match, not the full `<prop>AllVersions` family the spec's gadget description (§4.2.7) lists as an example — confirmed by reading the builder code (`StackGraphBuilder.java:159`, single `"allVersions"` pop). This is spec-permitted ("the spike measures how well this static rule matches") but the *scope actually implemented* is narrower than the spec's own descriptive text suggested, and (per Gap 5 above) is completely untested. It is also, per Gap 5's added disclosure above, built from `properties`/`qualifiedProperties` lists *after* `MilestoningPropertyProcessor` has already mutated them (synthesized `<prop>AllVersions`/edge-point/qualified properties present, original milestoned properties diverted to `originalMilestonedProperties`) — the one confirmed exception to the "builder reads only parse-time information" discipline claimed elsewhere in this report and in `StackGraphBuilder`'s own class javadoc.
3. **The harness force-resolves expected answers** via `ImportStub.processImportStub`/`processEnumStub`/`processPropertyStub` in test code (`TestStackGraphResolutionParity.forceResolve`), mirroring exactly what `BinaryModelSourceSerializer.java:552-560` does when serializing PAR archives. This is necessary because normal compilation sometimes leaves `resolved*` lazily unset (observed for `EnumStub.resolvedEnum` under the top-level-instance-literal construction path) — without it, the harness's "expected answer" would itself be incomplete. This call is test-only scaffolding, never present in `StackGraphBuilder.java`, and is the same sanctioned public API Pure's own serialization path uses.

## Recommendation

**GO for Phase 1** (stack graph as an invalidation index), with the following required design revisions before Phase 1 scope is finalized:

**Why GO:** the evidence is strong on the dimension that matters most for an invalidation index — *correctness of what the graph does resolve*. Across 14010 real platform references, spanning three independently-run full builds, the stack graph never once produced a **different, wrong** answer than Pure's own resolver (0 MISMATCH, always). The 0.079% residual gap (11 NOT_FOUND) has a single, precisely diagnosed, cheaply-fixable root cause (Package elements are never registered as their own pop-chain definitions) rather than a diffuse set of unexplained failures. The negative-parity fixtures agree with Pure's compiler 3/3 on outcome. This is a materially better signal than "close to passing" — it is "correct everywhere it was actually exercised, with one small, understood, fixable hole."

**Why not an unqualified GO:** the 99.921%/0-mismatch headline is an **ImportStub-only** result. `EnumStub` and `PropertyStub` — including the association and milestoning mechanisms that route entirely through `PropertyStub`/member-scope lookups — have **zero platform-scale validation** and, in milestoning's case, **zero validation of any kind**. A real cross-file capability (inherited-member lookup) was silently lost and only caught by review, not by any automated gate, because the corpus that would have caught it (real `PropertyStub` usage) doesn't exist in this repo's platform sources. Phase 1's invalidation index will need to reach correctness on these paths too if it is to cover the DSL/store repos (mapping, relational, etc.) where projections and associations are actually used in anger — this spike's platform-only scope did not test that.

**Required design revisions for Phase 1:**

1. **Close the Package-definition gap** (Gap 1) — a low-cost gadget fix, should land before or alongside Phase 1's first cut, not deferred.
2. **Design a real cross-file generalization/member-lookup mechanism** (Gap 3) — the spec's own suggestion (a non-completable, per-class "member-lookup" entry point distinct from the name-completion pop, reachable via root-judgment) is the right shape; this is genuine design work, not a gap-iteration patch, and is a prerequisite for Phase 1 if inherited members across files are in scope.
3. **Validate against a corpus that actually exercises `PropertyStub`/associations/milestoning** — either extend Phase 1's target corpus to include the mapping/relational DSL modules (where projections and associations are real), or explicitly scope Phase 1 to exclude those Pure constructs until validated. Do not carry forward the 99.921% figure as evidence for these paths.
4. **Add the missing test coverage before trusting these gadgets**: a milestoning fixture (currently absent entirely), a multi-candidate association over-approximation stress fixture (to measure false-positive rate, not just confirm the happy path), and a diamond/multi-supertype generalization-order fixture (spec §7's order-sensitivity question is currently unanswered, not "answered no").
5. **Budget for query-time indexing before Phase 2/3** (not necessarily Phase 1, which only needs invalidation, not full resolution): per-query cost (~66–82 ms median-to-max) is fine for a ~14-minute batch spike over hundreds of files but was flagged by the implementer as a build-time cost concern too (`linkGeneralizations()` runs a full internal `PathSearch` per generalization at build time) — worth profiling before this graph is used interactively or incrementally.
